# Conflict claims

Read [evolution-review.md](evolution-review.md) first.
Present the claims, conditions, and current carriers before selecting a correction.

| Apparent conflict | Check |
|---|---|
| Feature works in one test and fails in another | Runtime, mode, platform, and test conditions |
| One person abandoned an option; another still uses it | Subject attribution |
| A selected route differs from an eligibility rule | Choice versus rule |
| Proposed structure differs from approved structure | Same deliverable and progression history |
| A plan differs from a completed outcome | Event dates and verified completion |
| A diagnosis differs from a repaired system | Historical defect versus current state |
| A specification differs from an example | Binding requirement versus illustration |

For each review, show:

- Exact event and memory IDs from the current read.
- Historical or current role for each claim.
- The precise claim difference and applicable conditions.
- Relevant paths, branches, current successors, and evidence.
- Separate proposed content, graph, and Timeline effects.

If both endpoints already lead to valid current knowledge, explain that history.
Do not rewrite old bodies to make the review summary look consistent.

A patched defect can retain a durable lesson or dated outcome.
Change the type only when its meaning requires that change.
Do not treat a past defect report as a live vulnerability or as worthless history.

Keep a transient observation separate from a durable preference or identity claim.
A temporary location does not replace a permanent address.
A suggestion from an assistant does not record the user's decision.
